# 尼康 Z30 WiFi 连接 Keep-Alive 机制解决方案

## 1. 背景与问题
当手机 App 连接尼康 Z30（及其他同类微单）的 WiFi 后，如果长时间没有数据交互，相机会触发“非活动连接超时”自动断开 WiFi。因此，应用端必须主动实现保活（Keep-Alive）机制。

## 2. 核心保活方案
*   **保活指令**：推荐发送 **`GET_DEVICE_INFO`**。该 PTP 指令极其轻量，处理速度通常在几毫秒内，不会占用带宽和相机性能。
*   **保活周期**：推荐设定为 **30 秒**。既能有效防止相机触发休眠（通常为1~5分钟），又不会造成信道拥堵。

## 3. 防冲突设计（关键环节）
为防止 30 秒周期的 Keep-Alive 与耗时的图片下载/读取操作发生冲突，需在 `CameraRoll.kt`（或相应的通信层）中采用**阻塞锁与非阻塞锁结合**的并发控制策略：

### 锁机制设计
统一使用同一个锁（如 `gate`）进行控制：
1.  **图片下载/读取（高优先级）**
    *   所有耗时操作（如下载原图 `full()`、读字节流 `bytes()`、读缩略图 `thumb()` 等）必须走**阻塞锁**：`gate.withLock { ... }`。
    *   只要开始下载，就一直持有锁直到下载完成。
2.  **Keep-Alive 定时器（低优先级）**
    *   保活心跳必须走**非阻塞锁**：`gate.tryLock()`。
    *   拿不到锁时，立刻返回 `false`，直接跳过本次保活。

### 运行场景表现
*   **场景 A：下载正在进行中**
    锁被下载任务占用。此时 Keep-Alive 定时器触发，`tryLock()` 会直接返回 `false` 并跳过。做到**不抢锁、不排队、不打断下载**。此时由于有下载数据流，相机本来就不会断开。
*   **场景 B：Keep-Alive 正在执行时触发了下载**
    由于 `GET_DEVICE_INFO` 耗时极短（几毫秒），即使此时下载任务进场等待，最多也只需等几毫秒，用户完全无感知，不会造成卡顿。

## 4. 双重保险（可选）
在代码中引入状态拦截机制：维护一个状态变量（如 `saving`）。
*   当 `saving == true`（如下载高峰期、批量保存时），直接在业务层拦截并**不触发、不发送** Keep-Alive 指令，彻底为主流程让路。
