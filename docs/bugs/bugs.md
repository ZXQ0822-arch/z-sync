一条一个勾。**勾上 = 改完并在手机上验过；空着 = 代码已合入，但没有逐条复核。**

## 断流问题怎么分

下面四条不能合成一个「相机 Wi-Fi 不稳定」：

1. 空闲时 Android 主动离开无网热点，系统先 `onLost`。
2. 人划掉应用，进程结束，NetworkRequest 随之释放。
3. PTP 传输先失败，但 Wi-Fi 仍然有效。应用不应把它升级成 `NetworkLost`。
4. 相机待机定时器到了，热点真正消失，Android 随后 `onLost`。

共同验收是日志必须能判断谁先发生。只有第 1、4 类需要重获 Wi-Fi；第 3 类先保留网络并恢复 PTP；第 2 类允许结束会话。

## 空闲时手机离开相机热点

- [ ] 记录。0.1.20 上看到。不是应用发出的关热点指令。菜单见 [第一次用](../guides/setup.md)。传图过程中断掉的是下面单独一条。

2026-10-22 空闲时断了三次：大约 20:41、21:27、21:44。都是手机先离开相机热点，再回到家里的 Wi-Fi。不是在传照片。

第一次大约 20:41。手机后来自己离开相机热点，再连上家里的 Wi-Fi。

第二次是 21:27，当时手机上是 0.1.20。21:27:42 连上 `NIKON_Z_30_12345`。21:27:44 相机关掉了这一次 PTP 连接，应用重试了一次。21:27:50 手机本地断开，系统记的是 `CMD_UNWANTED_NETWORK`，`locally_generated=1`。这条热点不能上网，手机会把它丢掉。应用是在这之后才放开网络请求。21:27:52 扫描里还能看到这台相机，所以那一刻热点还开着，手机随后又连上了。

应用没有发关热点或关机的指令。断线时只关掉 TCP，没有发 `CloseSession`。

这条的直接触发者是 Android：`CMD_UNWANTED_NETWORK` 发生在应用释放回调之前。修复目标不是伪造热点一直有网，而是让长期相机会话持续持有明确的 NetworkLease，并在 `onLost` 后重新获取同一热点。空闲断线不能和 PTP 操作失败走同一个事件。

相机自己也会关热点：自定义设定 c3「待机定时器」默认大约 30 秒没人操作，屏幕关掉，热点跟着断。这和上面手机主动离开是两件事。

## 传图过程中热点断掉

- [ ] 代码已合入。PTP 失败不再释放 Wi-Fi，队列从安全偏移继续。

第四次是今天 21:47 左右，正在传照片。相机上的传输灯在闪，说明 PTP 正在通信，然后热点断了。

这和 20:41、21:27、21:44 不一样。那三次是空闲时手机离开热点，回到家里的 Wi-Fi。

21:47:39 手机重新连上相机，密码握手成功。这一段里没有新的照片连接失败。

传图过程中热点不应自己断。

代码审计发现一条可以造成同样现象的高风险路径：`PhotoViewModel` 把同步中的 `IOException` 交给 `cameraGone()`，`WifiCameraLink` 随即处理成 `NetworkLost` 并调用 `AndroidCameraWifi.release()`。如果这时 Android 的相机 `Network` 仍有效，应用反而会主动注销维持无网热点的 `requestNetwork`。

验收：

- PTP 超时或 TCP 关闭时，先记录 PTP 错误，NetworkLease 仍在。
- 在同一个 `Network` 上重试操作或重建 PTP 会话，照片队列暂停但不丢失。
- 只有 Android 明确 `onLost` 才重获 Wi-Fi。
- 恢复后从当前文件的安全偏移继续；已经完整保存的照片不重下。
- 整段日志里不能出现「PTP 错误 → 应用主动 release → 手机离开热点」。

## 刚连上、缩略图还在加载时跳回等系统确认

- [ ] 代码已合入。缩略图失败留在照片页，显示「正在恢复相机连接」。

21:55:09 对得上。应用进程还在。它放开了相机这条网络请求，手机马上本地断开。大约一秒后又重新请求加入，所以界面停在等系统确认。

别人处理这种没网热点的做法：请求里不要要求能上网，并且一直登记着这次网络回调，不要中途放开。放开之后手机会丢掉这条热点。前台服务本身留不住它。套接字要绑在相机这条网络上，手机原来的上网可以继续走蜂窝。相机那边没有「没网就关热点」；客户端一断，相机会结束连接，待机定时器到了也会关。PTP 中断时不要立刻放开 Wi-Fi 请求，应先重试这一次会话。见这次查到的 [Android 10 保持无网上的设备热点](https://stackoverflow.com/questions/62277005/how-do-i-keep-android-connected-to-an-iot-wifi-ap-with-no-internet-access-when-a)、[SnapBridge：应用退到后台会断](https://nikonimglib.com/snbr/onlinehelp/en/wifi_st_mode_connection_6.html)。

代码审计已经对上这条触发链：加载缩略图时 PTP `IOException` 可以触发 `cameraGone()`，随后应用调用 `release()`；`MainActivity` 看到状态不再是 `Connected`，马上撤掉照片页并关闭 CameraRoll。这不是相机热点先消失。

验收：

- 缩略图失败时保留已经显示的照片和照片页。
- 页面显示「正在恢复连接」，不跳回系统确认。
- PTP 会话恢复后从失败的对象或当前批次继续。
- 恢复失败时给「继续连接」和「取消连接」，只有确认取消才释放网络。

## 连接过程里的提示看不出在做什么

- [ ] 「允许」已拿掉。正在连接和等系统确认会转圈。首页有密码框；有上次记录时下面是「上次连接」，按钮是「重新连接」。热点不再列成可点列表；返回页按 HTML 显示静态找到的相机。

密码页、正在连接、等系统确认，这几屏的提示应说清楚现在在等什么，让人知道下一步发生什么。

「正在连接」通常只要一两秒，但上面没有转圈，也没有第几次尝试。前面找相机的那一屏会写「已扫描 N 次」。

「等系统确认」也一样。停在这一屏时，现在看不出它在做什么。应有转圈，让人看见它还在等。应用上的「允许」拿掉。密码提交之后自己去连，这一页只转圈。不要「允许」，也不要「请点允许」。

次数在连上时归零。从等系统确认或其它任何一页点「返回」，回到连接首页，不要自动连接。首页始终有密码框和原来的连接按钮。有上次记录时，密码框下面的状态行是「上次连接 [SSID]」，例如「上次连接 NIKON_Z_30」。下一行单独是「重新连接」。点「重新连接」才自动寻找并连接，不用再输入密码。扫描在后台继续，返回页按 HTML 显示静态找到的相机，不做可点列表。

正在连接和等系统确认都应能看出正在进行。密码页的提示也要一样清楚。

## 找不到相机这一屏走不回去，提示也太晚

- [ ] 代码已按设计稿对齐。找不到相机页是「连接已超时一分钟」和「请确认相机Wi-Fi已打开」，不写「扫描一次」。返回不再自动加入。

从第一次扫描起就应写：「相机可能没开机或不在旁边，请打开相机的 Wi-Fi，连接后再试」。现在要扫到第 5 次才出现类似的话。

次数单独写短：扫描一次、扫描两次。不要再写成「找不到相机，已扫描六次」这种长句。

点「返回」回到连接首页，不要自动连接。首页有密码框和连接按钮。有上次记录时，密码框下面是「上次连接 [SSID]」，按钮是「重新连接」。扫描在后台继续，返回页显示静态找到的相机。现在已经存了密码时，返回会再去加入热点。加入不成就又回到找不到相机，人被困在扫描里。

## 相册里已有副本时，去重、预览、删除都失效

- [ ] 0.1.25 上看到。日志 `decode saved handle=689537078 bytes=0`、`gallery delete name=DSC_0054.JPG rows=0`。

去重、读原图、删除都按精确文件名查 MediaStore。保存时如果重名，MediaStore 会改成 `DSC_0054 (1).JPG`，之后按原名就读不到、删不掉。保存时记下实际落盘的文件名，读/删用它；去重忽略 ` (N)` 后缀。
